# Data boundary contracts

Application data crosses storage, HTTP, RPC, WebSocket, background-message, provider, and browser-persistence boundaries. Raw input belongs in a decoder. Domain operations consume named views and construct typed commands; a JSON dictionary or a type assertion is not a domain contract.

The existing HTTP and storage formats are compatibility formats. Stored documents, operation-specific views, response representations, and normalized UI models have distinct requirements. Shared transport contracts belong in `runtime/src/shared/`; server persistence contracts must not become part of a public client contract accidentally. Author portable sources in `runtime/src/` and regenerate their JavaScript and declarations together.

## Compatibility rules

- Retain existing coercions, defaults, status fallbacks, property presence, and missing-versus-null behavior in explicit compatibility decoders.
- Keep preserved source JSON private to storage/compatibility adapters. Do not add writes that persist decoded defaults or normalize retained bytes; existing cleanup and reconciliation writes remain at their original boundaries.
- Preserve extensions only where the existing operation merges them. Replacements must continue to discard the same fields.
- Preserve serialization order where existing fingerprints, source digests, or replay checks depend on it.
- Preserve error precedence, conflict decisions, cancellation boundaries, query counts, SQL ordering, revisions, scheduling, retries, and authentication policy.
- Keep coercion at the existing operation boundary. Eagerly converting an unused legacy field can introduce a failure in a branch that never previously read it.
- Model partial and unrecognized legacy records explicitly. A minimal playable match is not necessarily a valid public match snapshot; a pending timer fence is not a completed claim.
- Accept raw `unknown` at parsing boundaries and for caught exceptions. Opaque legacy extensions and provider diagnostics may remain JSON when no domain operation interprets them.

The type-only `shared/api-contracts` registry covers all 69 business method/path pairs. It describes wire bodies, path/query fields, JSON results, native empty/text responses, and socket upgrades. Existing route builders correlate each literal path with its parsed body and result before heterogeneous dispatch; dedicated parsers and serializers reference the same registry. Browser endpoint helpers infer the contract from the actual path and prevent body or validator arguments from widening it. Low-level JSON transports and retained Telegram command replies remain honest unvalidated boundaries. Withdrawal submission preserves the browser’s unvalidated `eventId: string`; the existing server validator narrows it to the prize catalog before domain handling.

Session enrichment and logout, event 304 responses and optional snapshot seeds, withdrawal 200/202 responses, presentation conflicts, socket admissions, X callback redirects/text failures, and the retired Telegram delivery route keep their existing formats and ordering. Fresh socket messages remain separate from retained reaction snapshots. Endpoint compile checks cover actual private helpers, parser/handler pairing, and exceptional transport shapes; no generated dispatcher, schema validator, or SDK is introduced.

Match-sync, invite-metadata, and wager snapshot JSON strings are comparison caches, not decoded domain records. Their inputs are already typed or normalized; preserve their opaque byte-comparison behavior. SQL-column presentation reads and local timer rows have separate validation requirements from JSON record decoding.

Events use opaque document handles at repository boundaries, operation-specific observations, and typed constructors and patches. Compatibility helpers retain legacy values only when copying or serializing them. `EventCompatibilityRecord` describes the existing wire header; `decodeEventView` produces the complete nested UI model without changing the legacy response. Raw persistence commands remain separate from domain commands so validation and error timing stay inside the existing D1 adapter.

Withdrawals use opaque records and lazy observations so unused legacy numeric fields are not coerced early. Public repositories expose named claim, release, block, submission, discard, and completion operations. Processing creation replaces the record, submitted reacquisition merges retained evidence, and completion performs the existing unconditional replacement. Generic transactions remain confined to the storage adapter; completed writes require their own constructor.

Canonical matches retain the distinction between a missing row, stored scalar or array values, operation-specific match documents, and public snapshots. Move and surrender operations use narrow observations and typed mutations, while creation normalizes only at the existing write boundary. RPC methods use the actual Durable Object capability and method-specific result decoders; serializable wire values remain separate from opaque local documents. Replay identity, batch ordering, authority retries, and the unchanged-sync fast path are preserved.

Timer claims distinguish retained evidence, pending fences, committed observations, and precise new claimed writes. Persisted effects expose opaque payloads with separate scheduling fields and named completion and retry targets. Compatibility delivery keeps legacy field interpretation at its existing storage and transport boundaries, while ordinary timer methods and fresh event commands retain concrete inputs. Claim expiry, replay timestamps, eager effect-page JSON parsing, sequential delivery, and alarm transactions are unchanged.

Invite sources use opaque documents with separate participant, access, rematch, event, projection, and rating views. Fresh manual, automatch, and event invite writes require concrete constructors; wager overlays have a distinct document type. Canonical participant validation remains stricter than mutation and wager observations. Password presence, retained event match keys, grouped update order, retired-field handling, source identity, and metadata error classification are preserved.

Automatch snapshots, writes, and recovery pages correlate each storage root with its record type. Named repair, claim, acknowledgement, and completion operations keep raw transactions inside compatibility adapters. Session and event intents retain opaque resource, mutation, effect, and creation payloads while fresh construction uses versioned contracts. Receipt response kinds, independent expiration revisions, retained extensions, validation timing, SQL ordering, source bytes, recovery budgets, and retry behavior are preserved.

Telegram messages, control state, delivery evidence, cleanup queues, recovery requests, and projection state use opaque retained documents with named observations and transitions. Fresh provider requests, operation results, announcements, and retry schedules have concrete contracts. The transitions preserve uncertain send evidence, receipt-before-cleanup ordering, generation and lease fences, retained extensions, and proof reads across asynchronous boundaries. Shared event projection-outbox persistence is tracked with stage 9; progress Workflow persistence is tracked with stage 14.

Profile-game, event, and profile-link projections use opaque retained documents and operation-specific observations. Fresh projection commands distinguish create, update, merge, and delete payloads and flags. Canonical profile legacy evidence, auth-operation metadata/results, and rating payloads retain their original identity and serialization order behind named compatibility views; fresh writes use concrete state contracts. Shared event projection outboxes correlate their stored kinds and expose named recovery operations while preserving malformed-row accounting, source-byte guards, SQL ordering, and lease behavior.

WebSocket admission constructs concrete channel, protocol-version, identity, and session attachments. Resumed attachments and their raw invite/match keys stay opaque, with named observations preserving optional access, repeated reads, historical tags, authentication truthiness, expiry coercion, and original validation timing. Stored reactions retain arbitrary parsed JSON for the existing snapshot wire format; new reactions and socket messages use explicit contracts. Comparison-cache JSON remains opaque.

Frontend connection methods expose their concrete result contracts. Apple and wallet capabilities keep external outcomes unknown until their named readers or native byte conversion establishes a usable value. ENS consumers validate names while preserving whitespace, session and cache guards, repeated observations, and supported avatar absence. Session-token claim narrowing retains the existing timing policy. Browser persistence remains a separate compatibility boundary.

Browser persistence uses key-associated decoders and write contracts. Textual keys retain raw numeric and boolean-looking text and unwrap JSON-quoted strings; EmojiId preserves its existing JSON-first string-or-number interpretation. Missing values and the exact `null` sentinel keep caller defaults, nullable fields remain nullable, and sticker reads keep their serialized-object or legacy-string convention. Invalid unsupported shapes use the key's fallback without rewriting storage.

Navigation caches, pending moves and rematch endings, Apple intents, and logout/session records decode unknown evidence before domain use. Existing expiry cleanup, Apple intent reconciliation, scope ownership, operation-only confirmation, timestamp coercion, and restoration cloning remain in place. IndexedDB sessions retain validated original rows and extension fields for no-op comparison and in-place updates; malformed present rows fail closed instead of creating a new identity. Logout and session-reset keysets, provider behavior, and session-generation fences are unchanged.

The six registered Queue consumers are auth recovery, profile-game projection, event profile-game projection, Telegram projection, Telegram delivery, and wager settlement. Telegram delivery also recognizes the supported legacy wager-settlement message format. Every consumer starts with `Message<unknown>` and preserves its existing parser, acknowledgement, forwarding, and retry policy. The two Workflows are event progress and prize withdrawal, including the withdrawal preflight variant.

Queue producers use a keyed six-binding message map and strict function-property capabilities for single sends and generic batch recovery. The accessor returns the original binding, preserving the receiver, method lookup before argument evaluation, argument count, native response metadata, synchronous failures, and Promise identity. A union of binding names cannot admit a message that only one possible binding supports. Consumer parser inputs remain unknown, including supported legacy forwarding.

Event progress persistence distinguishes fresh pending records and dead letters from opaque retained pending/dead evidence. D1 reads and recovery snapshots preserve raw values and source bytes; the partial storage validator retains its existing limited checks and does not claim a fully validated Workflow plan. Generic retained-record transactions remain private adapter capabilities. Retained Workflow dispatch uses an explicit compatibility transport while fresh Workflow bindings stay concrete. Source-byte guards, scan accounting, SQL/CAS behavior, announcement timestamp merging, parser order, and recovery sequencing remain unchanged.

Scoped compile and source checks cover Queue family pairing, strict batch variance, fresh-versus-retained progress commands, opaque field access, private updater ports, and concrete Workflow inputs. The portable runtime export inventory must cover every generated module before checking each module's preserved value exports.

## Validation

Each changed boundary needs compatibility cases for its accepted representations, invalid outcomes, and write serialization. Assert decisions and observable output, not merely the new type definitions. Use compile-contract tests for endpoint pairing, write-state combinations, and repository return types.

Run focused Node/Workers tests and the affected lint/typecheck commands for each stage. Portable source changes also require `npm run generate:runtime` and `npm run check:runtime`. Final integration requires `npm run check:all` and `npm run build`.

No schema migration, stored-data rewrite, endpoint/protocol version change, OpenAPI publication, SDK, or third-party access is part of this work. Rendering-only types are outside this boundary inventory.
